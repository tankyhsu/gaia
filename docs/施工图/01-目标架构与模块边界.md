# 01 目标架构与模块边界

## 1. 总体结构

```text
Business Builder
  -> Gaia Docs / Dev Console Quick Start
  -> Scenario Template + Samples
  -> Generated Application

Developer
  -> Gaia Docs
  -> CLI / gaia.yaml / Python API / Gaia Test Kit
  -> GaiaApplication
       -> Config Loader + Profile Resolver
       -> Starter Registry + AutoConfigurator
       -> GaiaApplicationContext
            -> ModelProvider
            -> EmbeddingProvider
            -> WorkflowProvider
            -> ContextProvider
            -> ToolRegistry
            -> PolicyProvider
       -> Execution Runtime
       -> Actuator
  -> Gaia Dev Console（可选、开发期观察与诊断）
```

业务构建者和开发者共享生成应用及 Gaia Runtime，但入口不同。业务构建者不需要先理解组件图和
API；开发者接手已验证的场景后，负责真实模型、数据、Adapter、测试和部署。

`GaiaApplicationContext` 是组件计划与运行实例的只读快照。配置阶段只有 Descriptor，进入
application lifespan 后才包含真实组件。Runtime 通过显式依赖获取端口，不自行定位具体实现。

Gaia Test Kit 位于应用外部，通过 `CaseExecutor` 驱动应用或 Runtime。Evaluator 与 QualityGate
属于开发期测试扩展，不是线上 `ApplicationContext` 的必备依赖。

## 2. 目标目录

```text
src/gaia/
├── application/        # GaiaApplication、生命周期、ApplicationContext
├── config/             # YAML、Profile、环境覆盖、脱敏、配置 hash
├── components/         # Descriptor、ComponentSpec、Factory、资源作用域
├── starters/           # 内置 Starter 声明与自动配置条件
├── actuator/           # info/components/config/health 只读投影
├── cli/                # init/check/doctor/add-workflow/dev/starters/migrate
├── contracts/          # 与业务无关的公共模型
├── sdk/                # 应用作者实现的端口
├── runtime/            # Run、Policy、Gate、Command、恢复
├── model_gateway/      # Provider 实现
├── context/            # Context Provider 实现
├── workflow/           # Workflow Engine Adapter
├── integrations/       # 成熟第三方库与基础设施 Client 绑定
├── capabilities/       # Outbox 等可选行为包
├── persistence/        # Runtime、Replay 与 Outbox 持久化
├── evals/              # 通用 fixture/replay 引擎
├── testing/            # Test Kit 公共模型、扩展协议与开发期运行器
├── diagnostics/        # 通用诊断与脱敏
└── api/                # Runtime API + Actuator 路由

examples/controlled_task/
├── gaia.yaml
├── app/                # Intent、规则、Workflow、Mock Tool/Context
├── specs/
├── evals/
└── tests/
```

## 3. 组件分类

当前 `ComponentKind` 固定为：

```text
model
embedding
workflow
context
tool
policy
evaluation
diagnostics
persistence
checkpoint
memory
vector
cache
rate_limit
outbox
event_publisher
client
```

每个 `ComponentDescriptor` 至少包含：

- `component_id`：稳定、全局唯一；
- `kind`；
- `implementation`：Python import path 或外部协议标识；
- `version`；
- `starter_id`；
- `profile`；
- `status`：configured/healthy/degraded/failed；
- `replaceable`；
- `configuration_keys`；
- `depends_on`；
- `scope`：`static` 或 `application`；
- `reason`：为何被装配；
- `health`：最后检查时间与错误码。

## 4. 依赖方向

```text
cli/api/console -> application/actuator
application -> config/components/starters
runtime -> sdk/contracts/components/persistence
starters -> sdk/components + integrations/capabilities
integrations -> sdk/config
capabilities -> sdk/persistence/integrations
examples -> sdk/contracts/application
actuator -> application/components/config
```

禁止：

- `runtime -> starters`；
- `runtime/sdk/contracts -> integrations/capabilities`；
- `integrations -> application/starters/runtime/capabilities`；
- `capabilities -> application/api/starters`；
- `runtime -> examples`；
- `runtime -> context.mock/model_gateway.mock`；
- `config -> runtime`；
- `components -> FastAPI/React`；
- `examples -> persistence internals`；
- Dev Console 直接读取数据库、静态伪造组件状态或进入生产服务图。

## 5. Starter 契约

```python
class GaiaStarter(Protocol):
    descriptor: StarterDescriptor

    def defaults(self) -> dict[str, object]: ...
    def conditions(self) -> list[AutoConfigurationCondition]: ...
    def contribute(self, registry: ComponentRegistry, config: GaiaApplicationConfig) -> None: ...
```

M1 内置 Starter：

| Starter | 提供能力 |
| --- | --- |
| `core-runtime` | Runtime、Persistence、Diagnostics |
| `model-mock` | Deterministic Mock Model，用于测试 |
| `model-openai-compatible` | OpenAI-compatible Model Provider |
| `embedding-openai-compatible` | OpenAI-compatible Embedding Provider |
| `workflow-langgraph` | LangGraph Workflow Adapter |
| `context-mock` | 通用测试 Context Provider |
| `policy-controlled` | Policy、HumanGate、SideEffect Ledger |
| `evaluation-fixtures` | fixture loader 与 replay |
| `persistence-postgres` | PostgreSQL 事务型运行数据 |
| `checkpoint-sqlite` / `checkpoint-postgres` | LangGraph 线程内 checkpoint |
| `memory-postgres` | 跨线程、跨 Run 的长期记忆 |
| `vector-pgvector` | 长期记忆的 pgvector 语义索引 |
| `redis-client` | application-scoped redis-py Client |
| `cache-redis` | 带 namespace 和 TTL 上限的 Redis CacheProvider |
| `rate-limit-redis` | Redis Lua 原子固定窗口 RateLimiter |
| `publisher-in-process` | 单进程 EventPublisher |
| `outbox-postgres` | PostgreSQL Transactional Outbox |

示例应用可以注册自己的 Starter，例如 `controlled-task-example`，但该 Starter 不进入框架默认配置。
`evaluation-fixtures` 是现有 Replay 兼容 Starter；新的 Test Kit 作为开发期 Python API 使用，首版
不要求生产应用装配它。

## 6. 扩展发现

M1 同时支持：

1. 内置 Starter 显式注册；
2. `gaia.yaml` 中通过 import path 注册应用 Starter。

Python entry point 自动发现列入 M2，M1 不因插件生态提前增加打包复杂度。

Starter 只产生装配规格。`configure()` 不实例化组件；普通 Factory 和 Resource Factory 的详细
边界以[11-Python 原生生命周期与集成边界](11-Python原生生命周期与集成边界.md)为准。

## 7. 兼容性

- 原 `/v1/runs`、HumanGate、Replay 与 SSE API 在 M1 保持兼容；
- `/health/*` 保留，并与 Actuator 共享同一应用状态；
- 新增只读 `/actuator/*`；
- 旧 `controlled-task` 请求转由示例 Starter 装配，不再由 Runtime 硬编码；
- 数据库迁移新增 Outbox，并退役未被产品使用的配置控制面表；不重写历史 Run。
