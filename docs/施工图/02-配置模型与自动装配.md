# 02 配置模型与自动装配

## 1. 配置是框架公共契约

`GaiaApplicationConfig` 是 YAML、Profile、环境变量和 CLI 的唯一配置模型；Dev Console 只读
投影解析后的结果。

```yaml
gaia:
  application:
    name: controlled-task
    version: 1.0.0
  profile: mock
  starters:
    - core-runtime
    - model-mock
    - policy-controlled
    - evaluation-fixtures
    - import: examples.controlled_task.starter:STARTER
  runtime:
    database_url: sqlite+aiosqlite:///./var/gaia.db
    max_steps: 32
    timeout_seconds: 120
    environment: mock
  stores:
    operational:
      provider: sqlite
      auto_create: true
    checkpoint:
      provider: sqlite
    memory:
      provider: disabled
    vector:
      provider: disabled
  model:
    provider: mock
    model_id: deterministic-mock
    timeout_seconds: 2
  embedding:
    provider: disabled
  workflow:
    provider: langgraph
  context:
    provider: mock
  policy:
    provider: controlled
    human_gate_ttl_seconds: 86400
  prompt:
    provider: file
    root: prompts
  rag:
    provider: disabled
    root: documents
  evaluation:
    cases: ./specs/acceptance-cases.json
  profiles:
    sandbox:
      runtime:
        environment: sandbox
        write_mode: approval_required
    customer:
      runtime:
        environment: customer
        write_mode: disabled
```

## 2. Profile 与覆盖顺序

从低到高：

1. Pydantic 模型默认值；
2. Starter defaults，按 `starters` 声明顺序合并；
3. `gaia.yaml` 基础配置；
4. `profiles.<active>`；
5. `GAIA__SECTION__KEY` 环境变量；
6. CLI `--set section.key=value`；

每个最终字段必须记录 `ConfigOrigin`，用于 Dev Console 展示来源。数组默认整体替换，不做隐式拼接。

## 3. 环境变量

统一使用双下划线表达层级：

```text
GAIA__PROFILE=sandbox
GAIA__RUNTIME__ENVIRONMENT=sandbox
GAIA__MODEL__BASE_URL=http://model-gateway:8000/v1
GAIA__MODEL__MODEL_ID=local-qwen
```

配置文件路径不是配置模型字段，按 `--config`、`GAIA_CONFIG_PATH`、当前目录 `gaia.yaml` 的顺序
选择。旧 `GAIA_CONFIG` 仅作为兼容入口，并给出迁移到 `GAIA_CONFIG_PATH` 的明确提示。

只有已知的旧式配置覆盖变量会触发 deprecation warning。`GAIA_API_KEY`、SecretRef 指向的变量和
`GAIA_DEVTOOLS_ENABLED` 等控制变量不参与配置字段扫描，也不会被误报。`prompt.root` 与
`rag.root` 的相对路径以配置文件所在目录为基准解析。

## 4. Runtime Environment 与 Profile

Profile 是一组配置覆盖，可以叫 `postgres`、`dev` 或其他名称；`runtime.environment` 才是
`mock/sandbox/customer` 安全模式。两者相关但不等价。

未显式配置 `runtime.write_mode` 时：

- `mock -> enabled`；
- `sandbox -> approval_required`；
- `customer -> disabled`。

Sandbox 不允许配置为 `enabled`。Actuator 输出解析后的有效 write mode，而不是 `null`。完整规则见
[Runtime 安全边界与 Sandbox](09-Runtime安全边界与Sandbox.md)。

## 5. Secret

配置模型只保存 `SecretRef`：

```yaml
api_key:
  env: OPENAI_API_KEY
```

数据库连接串同样使用 `SecretRef`：

```yaml
runtime:
  database_url:
    env: GAIA_POSTGRES_URL
```

M1 支持 `env` 和 `file` 两种引用。Actuator、Dev Console、日志和诊断包都不得
保存解析后的明文。

## 6. 存储模型

`stores` 将四种职责分开，`runtime.database_url` 是 operational store 的主连接串，checkpoint 和
memory 可通过自己的 `database_url` 覆盖；未设置时继承主连接串。

| 配置 | 职责 | Provider |
| --- | --- | --- |
| `stores.operational` | Run、Gate、Command、Replay 和审计事件 | `sqlite` / `postgres` |
| `stores.checkpoint` | LangGraph 线程内暂停、恢复和状态快照 | `memory` / `sqlite` / `postgres` |
| `stores.memory` | 跨线程、跨 Run 的长期记忆 | `disabled` / `postgres` |
| `stores.vector` | 长期记忆语义索引 | `disabled` / `pgvector` |

`pgvector` 必须与 PostgreSQL memory store 同时启用。索引维度、距离算法、HNSW/IVFFlat 和字段均由
配置声明；embedding 可由应用组合根直接注入，也可以通过 `embedding-openai-compatible` Starter 配置。

```yaml
embedding:
  provider: openai-compatible
  model_id: Qwen/Qwen3-Embedding-0.6B
  base_url: https://api.siliconflow.cn/v1
  api_key:
    env: SILICONFLOW_API_KEY
  dimensions: 64
  batch_size: 32
  timeout_seconds: 30
```

`embedding.dimensions` 必须与 `stores.vector.dimensions` 一致。Provider 会校验返回数量、索引、
维度和非有限数值。硅基流动只是 reference profile 使用的兼容服务，Gaia 公共契约不绑定供应商。

### 6.1 Redis Cache 与 Rate Limit

`redis` 只提供连接参数；`cache.provider` 与 `rate_limit.provider` 分别决定是否装配对应组件。
`redis.url` 使用 SecretRef。Cache TTL 必须大于 0 且不超过 `max_ttl_seconds`。Redis 不作为
operational、checkpoint、memory 或 Outbox 的事实源。

### 6.2 PostgreSQL Outbox

`outbox.provider=postgres` 要求 `stores.operational.provider=postgres`。首版
`outbox.publisher=in-process`；`batch_size/lease_seconds/max_attempts/retry_delay_seconds`
均为启动配置，修改后需要重启。完整事务与投递语义见
[10-Redis 缓存、限流与 Outbox](10-Redis限流与Outbox.md)。

### 6.3 Prompt Provider

`prompt.provider=file` 使用 `prompt.root` 下的版本化 YAML，Starter 装配时不读取文件。
`prompt.provider=postgres` 要求 `stores.operational.provider=postgres`，并通过 0007 迁移创建
版本、环境指针和审计表。应用一次只选择一个 Provider，不混合优先级。

Prompt Artifact 内容不可原地覆盖；数据库发布只移动 mock、sandbox、customer 指针。Runtime
在创建新 Run 时解析指针，并把精确版本与内容哈希固定进 `VersionBundle.prompt`。

### 6.4 Cited RAG

`rag.provider=postgres` 显式装配最小有引用 RAG，并要求 PostgreSQL Memory、pgvector 和
Embedding 同时启用。未选择 Vector Store 时不自动激活。

`rag.root` 是参考 LocalFile Loader 可读取的根目录；`namespace_prefix` 隔离框架数据；
`chunk_size/chunk_overlap` 配置参考 Chunker；`candidate_multiplier` 为权限过滤和 inactive
generation 预留候选。Parser 属于可替换应用组件，Core 不绑定 Docling 或厂商解析服务。

## 7. 自动配置算法

1. 加载并验证基础配置；
2. 解析 active Profile 和覆盖；
3. 实例化 Starter descriptors；
4. 收集 defaults 后重新验证完整配置；
5. 逐个判断 Condition；
6. 注册普通 Factory 或 Resource Factory，不产生外部副作用；
7. 解析依赖图并检测缺失、重复和循环；
8. 生成 configured `GaiaApplicationContext`，组件实例映射为空；
9. 计算配置 hash 和组件图 hash；
10. 进入 application lifespan 后按拓扑顺序构造组件，由 `AsyncExitStack` 托管资源。

## 8. 条件类型

M1 只允许以下显式条件：

- `OnProperty(path, equals)`；
- `OnMissingComponent(kind|component_id)`；
- `OnComponent(kind|component_id)`；
- `OnProfile(name)`；
- `OnImportAvailable(import_path)`。

每个未生效 Starter 也要记录 negative match reason，类似 auto-configuration report。

## 9. 冲突规则

- 同一 `component_id` 重复注册：失败；
- 同一 `ComponentKind` 是否允许多实现由组件声明决定；Model、Workflow、Policy 默认单例；Tool 可多实例；
- 用户显式组件优先于 Starter 默认组件；
- 无法唯一选择必需组件：`CONFIG_COMPONENT_AMBIGUOUS`；
- 依赖缺失：`CONFIG_DEPENDENCY_MISSING`；
- 依赖循环：`CONFIG_DEPENDENCY_CYCLE`；
- Secret 无法解析：`CONFIG_SECRET_UNAVAILABLE`，错误中不得包含 Secret 值。

## 10. 配置变更边界

M1 不提供浏览器或 HTTP 配置写入接口。配置变更通过 `gaia.yaml`、Profile、环境变量或 CLI
覆盖完成，并由 Git、CI 和部署流程留痕。进程启动后 `GaiaApplicationContext` 保持不可变；
修改 Model、数据库、Redis、Outbox、Starter、Workflow、Context 或 Tool 配置后必须重启应用。
Actuator 的配置 hash 和字段来源是实际运行配置的事实来源。
