# Gaia 架构评审回复与增强计划

更新日期：2026-07-24

## 执行状态

- M0：已完成。五项 ADR、唯一 `ScenarioRunner` SPI、`WorkflowPort` 删除、引擎边界测试和
  `ModelInvocation` 证据模型均已落地。
- M1：已完成。已提供函数场景与工具 DX、`gaia init`、三种小型场景模板、按需组件选择、
  热重载、文件 Prompt Starter、仅初始化阶段可写入项目的新版 Quick Start，以及业务构建者/
  开发者双入口文档。
- M2：已完成首版。PostgreSQL Registry、Run 固定、质量门禁、CLI 和显式启用的开发期
  Prompt Workspace 已落地；A/B Variant 按原计划留到第二阶段。
- M3：已完成首版。统一 Wrapper、数据库证据、可选 OpenTelemetry Sink、Run 查询 API 和
  Dev Console 模型摘要已落地。
- M4：已完成首版。可替换文档契约、active-generation 摄取、pgvector 检索、权限过滤、
  Citation、Starter 和最小 Golden Dataset 已落地。
- M5：已完成受限首版。模型流式契约、五阶段 Guardrail、无正文决策审计、白名单 Handoff
  Pattern、Profile CLI 和 `gaia test` 已落地；开放式 ReAct 和自治多 Agent 仍不进入 Core。

## 1. 结论

评审对 Gaia 的核心判断成立：受控 Runtime、事务状态、幂等、HumanGate、副作用边界和可审计
运行证据，是 Gaia 相对普通 LLM 框架最有价值的部分。当前最需要增强的不是继续增加底层能力，
而是让业务构建者更快验证场景、让开发者更快接入这些能力，并补齐 Prompt 生命周期和模型调用
可观测性。

增强过程遵守四项原则：

1. Gaia 只有一套受控 Runtime，不为简单场景建立绕过安全边界的第二执行链。
2. 声明式 API 是公共契约的薄层，不把资源创建、网络 I/O 和隐式全局注册藏进装饰器。
3. Prompt 可以频繁创作和发布，但已发布版本及单次 Run 使用的版本不可变。
4. 新能力必须由独立应用和真实样本验证后才能进入 Core。

## 2. 对评审事实的校正

评审时以下问题真实存在；其中前三项已由 M0/M1 修复：

- 第一个应用的学习成本仍然偏高；
- `gaia dev` 当时没有热重载；
- Prompt 当时只有 `VersionBundle` 字段，没有 Artifact、Provider、发布和回滚机制；
- Model 调用曾缺少统一 Token、延迟、错误和成本观测，现已由 M3 补齐；
- Memory/Vector 之上的文档摄取与 Citation 检索闭环曾缺失，现已由 M4 补齐。

以下表述需要修正：

- Gaia Core 并未绑定 LangGraph。Runtime 的真实扩展边界是 `ScenarioRunner`；
- 评审时存在的 `WorkflowPort` 没有接入 Runtime，现已删除并收敛到 `ScenarioRunner`；
- `PostgresMemoryStore` 已基于 LangGraph `AsyncPostgresStore` 和 pgvector 实现；
- `examples/controlled_task/` 已是完整参考应用，问题是教学路径和开发体验不足；
- 当前架构是状态表加 append-only 审计事件，不是以事件重建全部状态的完整 Event Sourcing；
- Agent 可观测不等于保存模型私有思维链。Gaia 应记录输入输出引用、工具序列、模型用量和策略决策，
  默认不保存 Chain of Thought。

## 3. 对五项改进意见的正式回复

### 3.1 开发者体验

接受，列为最高优先级。

Gaia 将增加 `ScenarioSpec`、`FunctionScenarioRunner` 和薄层声明式 API。装饰器负责把普通 Python
函数及元数据转换为显式 Spec，不直接生成数据库连接、模型 Client 或其他 application-scoped
资源。

首版提供：

- `@scenario`：声明场景 ID、Prompt、Policy、Tool 和执行实现；
- `@read_tool`：从函数签名生成只读 Tool Schema；
- `@write_tool`：必须显式提供风险、角色、幂等和 `reconcile`，不能仅靠函数签名推断安全语义；
- `FunctionScenarioRunner`：承载单步调用和简单 Pipeline；
- `gaia dev --reload`；
- 生成项目中的可运行参考场景，而不只生成空方法。

### 3.2 Workflow 和 Agent 组合

部分接受。

近期优先提供确定性更强的 Function、Pipeline 和 Map-Reduce 模式。LangGraph 继续作为复杂状态机
的第一方 Adapter。Gaia 只增加受 `allowed_handoffs` 和 `max_handoffs` 约束的 Handoff Pattern；
开放式 ReAct、自治多 Agent 和 Reflection 不进入近期 Core，因为它们会扩大工具权限、循环预算、
恢复和 Sandbox 的安全问题。

### 3.3 LLM Observability

接受，但观测对象限定为工程证据：

- Provider、Endpoint、模型及参数版本；
- 请求、响应和结构化 Schema 的安全引用或哈希；
- input/output Token；
- 首 Token 和完整响应延迟；
- 重试、超时和错误分类；
- 可选成本估算；
- Tool 调用、Policy 决策、HumanGate 和最终业务结果之间的关联。

默认不记录明文 Secret、完整敏感 Prompt、客户原始数据和模型私有思维链。

### 3.4 Prompt 管理

接受，并作为 Gaia 的 AI 原生开发能力，而不是通用配置控制面的回归。

Gaia 将支持文件型和注册中心型 `PromptProvider`：

- `prompt-file`：默认零依赖，适合本地开发、简单应用和 GitOps；
- `prompt-postgres`：适合频繁调整、多人协作、发布、回滚和实验。

应用一次只选择一个 Provider，不隐式混合文件和数据库优先级。

### 3.5 RAG 管道

部分接受。

MemoryStore、EmbeddingProvider 和 pgvector 搜索已经存在；缺口位于数据摄取和检索组装。Gaia
只定义可替换的 Loader、Chunker、Retriever、Reranker 和 Citation 契约，并提供一条最小参考
Pipeline，不重新实现成熟文档解析库，也不把 RAG 做成独立平台。

## 4. 四个关键设计问题

### 4.1 DX 层与 Runtime

正式决定：

> `@scenario` 生成 `ScenarioSpec`，再由对应 Adapter 产生标准 `ScenarioRunner`。所有 Run 仍进入
> `PersistentRuntimeEngine`。

执行实现可以不同：

- 简单场景使用 `FunctionScenarioRunner`；
- 复杂、可暂停和多分支场景使用 `LangGraphScenarioRunner`；
- 未来其他引擎也只能在 `ScenarioRunner` 边界接入。

轻量实现可以不依赖 LangGraph，但不能绕过准入、事务、幂等、预算、HumanGate、副作用和审计。

### 4.2 Workflow 引擎

正式决定：

> LangGraph 是当前默认和第一方支持的 Workflow Adapter，但不是 Gaia Core 的永久唯一引擎。
> 近期不实现 Temporal。

在增加新引擎之前，先处理现有抽象：

- `ScenarioRunner` 保留为 Runtime 唯一 SPI；
- 删除未接入 Runtime 的 `WorkflowPort`；
- 增加引擎无关的契约测试，禁止 Runtime import LangGraph；
- LangGraph Checkpoint 和 Store 继续作为可选 Integration。

Temporal 自己拥有持久状态、事务和恢复语义，不是 LangGraph 的简单替换件。只有客户已有
Temporal，并且能明确划分 Gaia 与 Temporal 的状态所有权时才设计专用 Integration。

### 4.3 Prompt 存储

正式决定：

> 同时支持 File Provider 和 Registry Provider；文件是默认方案，数据库是频繁迭代场景的可选能力。

Prompt 数据模型：

```text
PromptRef
  prompt_id
  selector: version | environment alias | experiment

PromptArtifact
  prompt_id
  version
  content_hash
  input_schema
  messages
  model_requirements
  metadata
```

数据库版本状态：

```text
draft -> validating -> published -> retired
```

约束：

- Prompt 内容不能原地覆盖，每次修改产生新版本；
- mock、sandbox、customer 分别维护发布指针；
- Run 创建时解析并固定 Prompt 版本和内容哈希；
- 新版本只影响新 Run，不修改正在执行或等待人工的 Run；
- Replay 必须能解析或保存当时使用的不可变 Prompt Artifact；
- 回滚通过移动环境指针完成；
- A/B 通过显式 Variant 路由，Run 固定 Variant；
- Dev Console 可以提供开发期 Prompt Workspace，但生产 Runtime 不暴露任意编辑入口。

### 4.4 部署形态

正式决定：

> 逻辑部署单元是一个 `GaiaApplication`。一个应用可以注册多个相关 Scenario，并可以部署多个
> 共享数据库的副本。

不强制每个 Scenario 一个微服务，也不建议把企业全部场景放入一个超级单体。拆分依据是：

- 业务限界上下文；
- 数据和权限边界；
- 安全等级；
- 外部依赖；
- 容量和可用性要求；
- 发布周期及团队所有权。

多个 Gaia 应用通过 API Gateway、事件总线或外部业务编排协作。Gaia Core 不建设分布式
Scenario 注册中心。Scenario 共享应用级 ModelGateway、Persistence 和基础设施资源，同时拥有
自己的 Prompt、Policy、VersionBundle 和测试集。

## 5. 增强路线

### M0：契约收敛

目标：在增加语法糖之前固定真正的扩展边界。

交付物：

- `ScenarioSpec` 与 `ScenarioRunner` ADR；
- `WorkflowPort` 去留决定；
- Prompt Artifact/Provider ADR；
- 部署单元 ADR；
- LLM Invocation 观测事件模型；
- 架构测试禁止 Runtime 依赖具体 Workflow 引擎。

完成门禁：

- 不改变现有 Runtime 行为；
- `controlled_task` 全量回归；
- 公共契约中不存在两个含义重叠的 Workflow 执行入口。

建议投入：一个短迭代。

### M1：第一个场景的最短路径

目标：开发者不理解 Runtime 内部实现，也能创建受控场景。

交付物：

- `FunctionScenarioRunner`；
- `ScenarioSpec`；
- `@scenario`、`@read_tool` 和受约束的 `@write_tool`；
- `gaia init` 生成基础请求、知识检索或受控操作场景，并支持按需组件；
- `gaia dev --reload`；
- Quick Start 在初始化标记存在时提供场景与组件选择，完成后退化为只读说明；
- 文件型 `PromptArtifact` 与 `prompt-file` Starter。

完成门禁：

- 新目录执行 `gaia init` 后可以直接启动；
- 只读场景不手写 LangGraph；
- 写入场景仍强制经过 ToolDefinition、幂等、风险和 HumanGate；
- 生成项目拥有独立测试并通过 clean-wheel 黑盒验证；
- 新 DX 层不在 import 和 configure 阶段产生外部 I/O。

建议投入：一至两个迭代。

### M2：Prompt 生命周期

目标：允许业务高频调整 Prompt，同时保持可发布、可回滚、可测试和可复现。

交付物：

- `PromptProvider`、`PromptRef`、`PromptArtifact`；
- `prompt-postgres` Starter；
- Draft、Validate、Publish、Retire 和 Rollback 服务；
- Prompt 版本与 `VersionBundle` 自动绑定；
- Test Kit Golden Dataset 发布门禁；
- CLI 的 import、diff、validate、publish 和 rollback；
- Dev Console Prompt Workspace；
- 第二阶段再增加 A/B Variant。

完成门禁：

- 发布 Prompt 不需要重启应用；
- 新 Run 使用新版本，既有 Run 保持旧版本；
- 任意历史 Run 能解释所用 Prompt ID、版本和哈希；
- 未通过质量门禁的 Draft 不能发布到 customer；
- 回滚不修改历史版本；
- 默认 API 和生产服务图不包含 Prompt 编辑界面。

建议投入：两个迭代。

### M3：模型调用可观测

目标：把模型不确定性转化为可测量的工程事实。

交付物：

- 统一 `ModelInvocation` 与 Usage 契约；
- Instrumented ModelProvider Wrapper；
- 可选 OpenTelemetry Integration；
- Token、延迟、错误、重试和成本指标；
- Run、Prompt、Model、Tool 和评估结果的关联；
- Dev Console Run Inspector 与模型摘要。

完成门禁：

- Mock 和 OpenAI-compatible Provider 使用同一观测契约；
- 未配置 OpenTelemetry 时没有强制依赖；
- 观测失败不能改变业务 Run 结果；
- 默认日志不泄露 Prompt 明文、Secret 或客户原始数据；
- 不采集模型私有思维链。

建议投入：一至两个迭代。

### M4：最小 RAG Starter

目标：补齐从文档到有引用检索结果的最小闭环。

交付物：

- `DocumentLoader`、`Chunker`、`Retriever` 和 `Citation` 契约；
- 可替换 Parser Adapter；
- Embedding + PostgresMemoryStore/pgvector 组合；
- namespace、权限、版本和删除语义；
- 摄取结果、检索结果和来源引用；
- 一套小型 Golden Dataset。

完成门禁：

- Parser 可以替换，不在 Core 中硬编码 Docling；
- 相同文档重复摄取幂等；
- 文档更新和删除不会留下不可解释的旧 Chunk；
- 检索结果包含来源、版本和权限证据；
- 无 Vector Store 时不自动激活 RAG Starter。

建议投入：两个迭代。

### M5：Workflow Patterns 与生态扩展

触发条件：至少两个真实应用证明模式重复。

候选能力：

- Pipeline；
- Map-Reduce；
- 受限 ReAct；
- MCP Adapter；
- Temporal Integration；
- 多模型路由与 Fallback。

已先行落地最小 Handoff Pattern：Agent 注册、白名单路由、共享状态、交接轨迹和硬预算。它不负责
工具授权和持久恢复；应用仍在 `ScenarioRunner` 内使用该模式。开放式自治多 Agent、ReAct 和
Code Execution Sandbox 必须单独评审，不因 DX 需求自动进入 Core。

## 6. 当前执行顺序

M0 至 M5 的受限首版已经完成。下一阶段不继续横向堆积框架能力，优先用独立应用验证：

1. 五阶段 Guardrail 的策略组合、误报率、延迟与 fail-open/fail-closed 选择；
2. Retrieval 和 Tool 防护是否需要提升为自动装配的 Starter；
3. Prompt A/B、Test Kit 报告落库和更多 Workflow Pattern 的真实重复需求。

## 7. 明确不做

- 不建立绕过 `PersistentRuntimeEngine` 的轻量 Runtime；
- 不把所有装饰器直接编译为 LangGraph；
- 不允许生产 Prompt 原地覆盖；
- 不恢复通用配置 Revision Control Plane；
- 不默认保存 Chain of Thought；
- 不立即支持 Temporal、开放式自治多 Agent 或通用 ReAct；
- 不重新实现成熟文档解析器和向量数据库；
- 不把 Dev Console 变成生产业务后台。
