# 工程纪实：决策、缺陷与被否决的方案

这份文档记录 Gaia 一次完整重构（工程 A–H）中值得留下的部分：**做过的判断、
自己找出的缺陷、以及主动放弃的方案**。

它刻意不是功能清单。功能清单说明"做了什么"，而一个系统真正的形状，是由那些"没有做什么、
以及为什么"决定的。

阅读大约 20 分钟。每个结论都指向具体代码，可以自行核对。

---

## 一句话

Gaia 是面向 AI 工作流的**受控执行与审计运行时**。它要解决的不是"如何把 Model、Workflow、
Tool 拼起来"——AI 代码生成已经让这部分变廉价——而是拼起来之后：**谁能证明配置里声明的策略
就是线上真正执行的策略**。

七条控制可以用 `make attack-demo` 现场验证，每条都会打印执行拦截的代码位置。

---

## 一、三个真实缺陷

这三个都不是"功能没做完"，而是**"声称已强制、实际没有强制"**。这类缺陷的共同特征是：
测试全绿、文档齐备、监控面板正常，唯独控制本身是空的。

### 1. 一个假的治理开关

我实现了 `policy_overrides`，让运维可以在 `gaia.yaml` 里收紧策略而不改代码，其中包括
`deny_tools`——禁用某个工具。实现完成，测试通过，指纹证据也带上了。

然后我构造了一个探针：

```
覆盖后 policy.allowed_tools : []            ← 工具确实被移除了
内部 runner 仍持有的 policy : ['probe.lookup']  ← 但这里没有
```

`FunctionScenarioRunner._invoke` 用 `self.execution_policy` 构造 `ScopedToolExecutor`，
而 `self` 是**内层** runner——包装器上的收紧策略根本没传进去。结果是：

运维配了 `deny_tools: [customer-lookup]`，`gaia check` 通过，Actuator 显示策略已收紧，
审计证据带着 `+ovr.<指纹>` 为"该工具已禁用"背书——**而场景里 `ctx.tools.call()` 照样能
调到它**。

我最初的判断把这条写成了"既有架构属性、超出本任务范围"。这个定性是错的：本任务之前根本
没有 `deny_tools` 这个表达方式，谈不上既有；是本任务引入了这个开关，就该由它负责让开关
是真的。

**修法不是补一层同步，而是消除二元性**：在装配期用 `dataclasses.replace` 重写
`ScenarioSpec`，runner 直接由收紧后的 spec 构造，**结构上不存在第二份 policy**。
见 [`runtime/assembly.py`](../src/gaia/runtime/assembly.py)。

> **这是全篇最重要的一条**：宁可不提供这个控制，也不能提供一个假的。缺少功能只是缺少
> 功能；伪造出可审计、带指纹、被监控面板确认的"控制已生效"证据，会让依赖它的人在错误的
> 前提上做决定。

### 2. 组件图里没有可被消费的东西

最初的架构评估里我写：Runtime 不消费组件图，组件图只服务于 Actuator 展示。

真正动手接线时才发现问题更深一层。内置的 MODEL / WORKFLOW / CONTEXT / POLICY starter，
注册的 factory 是：

```python
lambda _components: {"starter": self.descriptor.starter_id}
```

**返回标记字典**。不是"Runtime 不去消费组件图"，而是**组件图的核心节点里压根没有可被消费
的东西**。

这直接改变了施工计划：原定的里程碑"声明式路径端到端跑通"，如果按原方案只能覆盖只读场景
——凡是调模型的场景仍需应用方手工传 provider，双装配问题在最常见的场景类型上原样存在。

于是新增了一个任务把 MODEL starter 改为注册真实实例，并**把里程碑的定义从"A4 完成"改为
"A4 + A4b 完成"**。按原定义达成时，框架仍然不能声明式地跑一个用模型的场景——那个里程碑
是虚的。

### 3. 两份实现，其中一份带竞态

`runtime/ledger.py` 里的 `RuntimeLedger` 提供 `append_event`、`create_run`、`add_gate`
等持久化原语,顶着权威名字和"Runtime ledger for Run, Event, Gate, and Command ownership"
的 docstring。**但生产代码从不使用它**——全库引用只有一个测试。

两份实现不是等价的，这才是留着它危险的原因：

| | 事件序号分配 |
| --- | --- |
| `RuntimeLedger` | `SELECT max(sequence) + 1` — 读后写，两个并发 append 会写出重复序号 |
| 引擎自己的实现 | `UPDATE ... SET event_sequence = event_sequence + 1 RETURNING` — 单语句原子自增 |

迁移 `0002_run_event_counter` 的 docstring 写得很明白:**"per-run event sequence counter
for concurrent-safe allocation"**。`RuntimeLedger` 就是 0002 之前的旧实现,修正版落地时
没人删掉它。

下一个读到 `ledger.py` 的人——无论是人还是 AI——都会以为它才是正主，然后采用那个带竞态的
版本。**所以答案不是"合并"，是删除。**

## 二、被否决的方案

架构判断的价值常常在这一节。

### 否决：运行时 monkeypatch

场景模块必须"导入期纯净"（不能在 import 时连数据库、解析 Secret）。最初方案是在扫描时
patch `socket.connect` 和 `resolve_secret`，把违约变成清晰报错。

否决理由：`socket.socket.connect` 是 C 层类型方法，patch 不保证稳定；patch 是**进程全局**
的，启动期其他线程会被误伤；目标模块若已 `from ... import resolve_secret`，patch 原模块
属性对它无效；而且它只能拦住少数 I/O 形式，**却会让使用者误以为得到了真正的隔离——这比
不做更危险**。

改为 AST 静态检查（[`diagnostics/import_purity.py`](../src/gaia/diagnostics/import_purity.py)），
不 import 目标模块，按**导入来源**解析后匹配白名单。

关键取舍：**按来源匹配，绝不按裸调用名匹配**。按名字匹配 `Client` / `connect` 会误报业务
方自己的类和任意对象的方法。而"宁可漏报不误报"不是保守，是必需的——**一个会挡住正确项目
的检查，会被绕开，然后它什么都保护不了**。

### 否决：为对齐数字继续拆引擎

计划里写了"引擎降到 800 行以下"。三次拆解后是 1146 行，剩下的是公开 API、核心编排、
以及三个协作者共用的账本管道。

我没有再拆一刀，而是**修改了目标值并写明理由**：为凑数字硬拆只会把耦合藏进新文件，
而不是消除它，这与"让人敢改"的初衷相反。承诺一个架构支撑不了的数字，只会产出一份没人
遵守的计划。

（后续 C2、D1 又向引擎加了租约与批次逻辑，一度到 1306 行，同样如实记录而非再拆。再往后
这台 SQL 引擎被 Temporal 整个取代并删除——那个行数目标最终是被"换掉这段代码"解决的，
不是被拆解解决的。）

### 否决：把 `GaiaAppBuilder` 当死代码删掉

我一度判定它"零测试覆盖"并开了清理任务。**这个结论是错的**——那条 grep 我加了 `| head`，
10 行全被 `builder.py` 自身占满，把 9 处测试引用截断了。

它有测试、有文档、且委托给 `RuntimeAssembler` 而非另起一套装配，是门面不是死代码。任务
作废，教训写进了施工卡：**判断"是否有人在用"要用 `grep -c` 或按文件聚合，不要用会截断的
`| head`**。

### 否决：把审计证据的版本号原样透传

策略被收紧后，`VersionBundle.policy` 一度保持不变——为了绕过一致性校验。这等于"实际策略
已收紧、审计版本没变"，正是本工程要消灭的问题。

改为把指纹编进策略版本号（`1.0.0+ovr.9c1d2f0a`），一致性校验自然满足，**不需要也不允许
放宽任何校验**。顺带一个细节：指纹的 `sha256:` 前缀含冒号，不符合 PEP 440 local version
规范，所以拼接时用裸摘要。

## 三、几处刻意的设计

**跨组织越权返回 404 而非 403。** 403 会向不该知情的人确认"这个资源存在"。一个不存在的
Run 和一个属于别的组织的 Run，从外部看必须无法区分。

**认证身份是唯一事实源，冲突时拒绝而非静默覆盖。** 请求体自称的 `roles` 直接参与
`safety.py` 的角色校验——信任它等于让调用方给自己授权。而静默覆盖会让调用方以为自己以
另一个身份执行了操作，所以冲突时返回 `IDENTITY_MISMATCH`。

**`AuthnProvider` 的三态是刻意分开的。** 抛异常=认证失败（401）；返回身份=该身份权威；
返回 `None`=已认证的可信服务、无终端用户身份。把后两者合并成一个值，会让"认证失败"和
"可信服务调用"走同一段代码，而它们的正确响应恰好相反——迟早会把失败的认证当作可信调用
放行。

**`at_most_once_manual` 的恢复预算是 0。** 另两种策略各有 3 次自动恢复预算，唯独它没有:
"最多执行一次，之后由人决定"这个语义，与"每次启动都重新走一遍"是矛盾的。真实结果无法
确定的写入以 `SIDE_EFFECT_UNKNOWN` 终止，并在运维视图里与"被控制拦下"分开列出——
**框架不提供把它改回去的 API**，人工处置需要独立的授权与审计设计，不能顺手加一个接口
了事。

**租约过期后绝不静默重取。** 过期意味着另一个副本可能已经认为自己持有它，静默续期会造成
两个副本同时执行同一批恢复。

## 四、现在能证明什么，不能证明什么

`make attack-demo` 一秒跑完，七个攻击全部被拦，每条打印执行拦截的代码位置。它**退出非零
当任何一条防御失败**，并且已纳入 pytest——一个不再被执行的防御，从退出码上看和仍然通过的
防御一模一样。

**不能证明的部分，同样明确**：

- 授权只到组织级。组织内部更细的权限是应用自己的责任。
- 稳态执行**没有**跨副本协调。租约只序列化启动恢复；两个副本可以同时执行各自收到的请求。
- 导入期纯净性检查是 best-effort 的 lint，会被普通间接调用绕过，不是隔离。
- 以上都不构成任何合规认证。

### Temporal namespace 是一条信任边界

把执行交给 Temporal 之后，**能连上那个 namespace 的人，就能直接给 Workflow 发消息**——
不经过 Gaia 的 API，因此不经过认证。Workflow 自己没有能力鉴别调用方，它的 `decide`
Update 只能相信 payload 里写的 `roles`。

这一条不能靠"写在文档里请大家不要这样做"解决，所以做了两处**执行路径上的**复核：

| 直连 namespace 能做什么 | 结果 |
| --- | --- |
| 伪造 `decide`，`roles=["approver"]` | Workflow 内部状态会变，**但写入不发生**。`execute_command` 在动手之前查 Gaia 自己的库，那里只有经过认证的 API 才写得进批准。见 `GATE_DECISION_UNVERIFIED` |
| 手工 start Workflow，绕过准入 | `run_scenario` Activity 用服务端 policy 重新跑一遍 `validate_run_admission`，环境模式与角色不符照样拒 |
| 伪造 `version_bundle` 写进证据 | **仍然可以**。版本证据在 create 时解析，Activity 不复核 |
| `cancel` 任意 Run | **仍然可以** |

前两条被堵住了，后两条没有。所以准确的说法是：**namespace 访问权不再等于批准权，
但仍然等于"能伪造版本证据、能中止任何 Run"**。要不要把 namespace 当作和数据库同级
的敏感资产来管控，是部署方的决定——但这个事实必须写在这里，而不是留给别人去发现。

关于第一条为什么这么做：批准这件事的权威记录放在 Gaia 的库里，Temporal 只承载"人已经
决定了"这个编排信号。这不是给 Workflow 加一道校验（Workflow 自己就是被伪造的那一方，
它校验不了自己），而是**把授予权限的能力搬到一个攻击者够不着的地方**。投影因此只允许
一个方向的写入：`record` 可以记录 gate、可以记录拒绝和过期（这些只会**收回**权限），
但永远不能把一个 gate 变成 `approved`；只有认证过的 `record_decision` 可以。

这份"不保证什么"的清单和能力清单一样重要。**明说框架不做什么，比暗示它做得更多要有价值。**

## 五、这一路验证方式的变化

这次重构中，实现工作大量由 AI 子智能体完成，我做架构判断和验收。七次打回，**每一次的
缺陷都不在功能上，而在"出错时告诉用户什么"和"控制是否真的生效"**：

| 缺陷 | 表现 |
| --- | --- |
| 模块依赖缺失 | 报"模块不存在"，把人指向一个完全正确的配置文件 |
| guardrail 部分映射 | 引擎深处抛 KeyError |
| 组件图假设被证伪 | 计划据此改写并新增任务 |
| `gaia init` 后第一条命令 | 让用户去改一个正确的配置文件 |
| `deny_tools` | 假开关 |

它们的自测每次都全绿——这些是**构造探针或读代码查出来的**。

这件事对"AI 生成代码已经很容易"这个前提有直接含义：**生成是容易的，验证不是。** 而验证
里最难的一类，恰恰不是"功能对不对"，是"你声称已强制的东西，是否真的被强制"。

一份清单能查的只是你想到要查的东西。上面那个假开关就在我自己写下"伪造可审计的控制证据
比没有控制更危险"之后，仍然从我的终态验收里溜了过去——它是**外部评审复现出来**的。
