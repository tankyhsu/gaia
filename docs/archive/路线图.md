# Gaia 路线图

架构评审后的正式答复、关键设计决定和近期增强里程碑见
[架构评审回复与增强计划](架构评审回复与增强计划.md)。

## 路线图原则

路线图不是功能愿望清单。只有能成为通用 AI 应用开发基线、并已由真实应用验证的能力才进入
核心；交付效率是验证价值的重要场景，但不再定义 Gaia 的产品身份。

## P0：通用交付内核

当前必须完成：

- Developer SDK 最小契约；
- Execution Runtime 围栏、状态、人工门禁和副作用边界；
- ModelGateway，支持 Deterministic Mock 与 OpenAI-compatible Endpoint；
- Workflow、Context 和客户系统 Adapter 契约；
- Mock / Sandbox / Customer 服务端环境、Tool 环境绑定和写入上限；
- Gaia Test Kit 的 Dataset、Evaluator、QualityGate 与结构化报告；
- 固定样本、围栏测试、运行证据和诊断包；
- 行业无关的 `controlled-task` 合成通路。

P0 不部署真实本地模型，但必须证明可以不修改上层场景地替换 Model Endpoint。
P0 的 Sandbox 只做集成环境隔离，不建设任意代码执行平台。

## P1A：可选基础设施扩展

当前已实现：

- Python 原生 application lifespan 与 Core/Integration/Capability Pack 边界；
- `cache-redis` 与 `rate-limit-redis` 可选 Starter；
- PostgreSQL Transactional Outbox；
- 进程内 Publisher，用于单进程开发和契约验证。

暂不实现 MQ Adapter。出现多 Worker、跨系统消费或企业消息平台接入后：

- 事件平台和事件流优先 Kafka；
- 工作队列、逐任务 ACK 与路由重试优先 RabbitMQ；
- 两者都实现 `EventPublisher`，不改变业务事务与 Outbox；
- Redis Streams 不替代可靠事件总线。

## P1B：业务应用复用

在第一个真实项目中验证：

- 客户身份、数据、Context 和源系统适配；
- 一个客户允许的真实模型 Endpoint；
- Endpoint 能力探测、评估、降级和运行审计；
- 第二个场景对 SDK 抽象的反向验证；
- 部署、回滚、移交和客户独立回放。

## P1C：可运维性

当前进入 Gaia 通用能力：

- 稳定机器码与人类可读错误、错误类别、重试语义、处理建议和 Trace ID；
- `gaia check` 静态校验与 `gaia doctor` 外部依赖诊断分层；
- Run、HumanGate、错误、Outbox 和数据库争用的通用运行摘要；
- 独立的 Gaia Dev Console：Quick Start 负责业务场景初始化，日常提供开发概览、组件、运行、
  只读配置和测试视图；
- 独立 Gaia 文档的双入口：业务构建者按 Demo 验证路径阅读，开发者按机制和接入路径阅读；
- 应用侧 Workflow 节点与路由模板，不把业务流程下沉到 Gaia。

Dev Console 不进入 Gaia Python 核心包，也不随生产应用部署；生产环境只加载应用声明的 Starter。

30 秒启动与 1 分钟排障 Runbook 保留为后续文档项。待错误目录和诊断能力在真实应用中稳定后再
编写，当前不投入单独建设。

## P1D：AI 原生开发基线

当前已实现：

- `ModelProvider.generate_stream()` 与 OpenAI-compatible 增量响应；
- 流式调用的首 Token、Usage、成功和失败观测；
- 覆盖输入、检索、输出、工具输入和工具输出的 Guardrail Pipeline；
- 版本化、无正文的 GuardrailDecision、SQLAlchemy Sink 和按 Run 查询；
- 明确的 fail-open/fail-closed 与强审计开关，以及通用 Pattern Guardrail；
- 可选 Presidio PII 适配器和 validate-only Guardrails AI 适配器；
- Builder、正式 Runtime 与 Scenario Test Harness 使用同一份五阶段 Guardrail 装配；
- Runtime 原生多 Agent Handoff：白名单路由、持久状态、共享 RunBudget、重启恢复，并可进入
  Write Tool / HumanGate；
- 写操作和 ActionPlan 完成后的持久化 Continuation，可根据真实 ToolResult 继续模型判断、
  Handoff 或下一次受控操作；
- 输出 Guardrail 的严格缓冲模式：有输出规则时只做一次全文检查，通过后才释放正文；
- Write Tool 的 `reconcilable`、`idempotent` 与 `at_most_once_manual` 恢复策略；
- 持久化 `run_budgets` 统一约束 Scenario、Agent、Read/Write Tool 和模型调用；
- 结构化输出有限纠偏：Schema 与显式 `correctable` Validator 可重试，安全阻断不重试；
- `--profile` 正式 CLI 参数，Profile 在进程启动时确定；
- `gaia test` Dataset 运行、结构化报告和稳定退出码。

当前边界：

- Run Event SSE 与模型正文流式是两套不同契约；
- Runtime Handoff 不提供开放式 ReAct、无限循环或任意工具授权；进程内
  `InMemoryHandoffOrchestrator` 不用于需要恢复或审批的流程；
- Guardrail Core 不内置行业敏感词、PII 类型或客户合规规则；
- 第三方 Guardrail 不固化默认策略或自动启用；HR Showcase 已完成首个 Guardrails AI
  validate-only 验证，Starter 仍等待更多应用验证误报、延迟与资源占用；
- 已归档的 LLM Guard 不进入默认依赖；NeMo 只在对话状态机需求出现时单独评估；
- Profile 不支持运行中热切换；
- Test Kit 的报告落库和 Dev Console 投影等待真实应用验证。

## P1E：业务构建者体验增强

核心能力已完成首轮实现和独立 Showcase 验收，详细边界见
[业务构建者体验增强计划](业务构建者体验增强计划.md)。

当前已实现：

- 统一 Read/Write Tool 注册、受限执行和观测；
- 通过 `ScenarioContext` 和 `GaiaAppBuilder` 收敛 Model、Tool、Runner 和 Runtime 装配；
- 在 `waiting_human` 状态保留业务草稿和独立审批展示信息；
- 用严格顺序的确定性 `ActionPlan` 支持一次 Run 中的多项受控操作；
- 提供 Scenario Test Harness 和轻量前端 Client，减少应用重复建设；
- Quick Start 和 Dev Doc 提供三个 Showcase 的能力链说明与体验入口，日常 Dev Console
  保持框架观测职责；
- 独立 HR Showcase 已验证 Read Tool、Model、规则、审批与多系统写入主线。

后续由真实业务需求触发的增强包括：并行动作组、合并审批、自动补偿和第三方 Agent Adapter。

这一阶段不实现 Gaia 自有 Agent Loop。未来接入 AgentScope、LangGraph 等成熟 ReAct 实现时，
第三方 Agent 只负责推理循环，并复用 Gaia 的 Scoped Tool Executor、Guardrail、Human Gate、
Action Plan、持久化和审计。

## P2：可选本地模型推理套件

只有当客户明确需要本地部署，且现有平台无法满足时，才评估独立的 `model-serving-kit/`：

- vLLM、TGI 或客户已有推理平台的部署 Profile；
- 模型制品 Manifest、健康检查和冒烟验收；
- GPU、量化、并发、显存和容量配置；
- 版本切换、灰度、回滚和离线安装；
- 向 Gaia 输出统一 Model Endpoint。

该套件与 Gaia 平级，不得成为通用脚手架的强制依赖。

## 独立触发项：Code Execution Sandbox

仅当 Gaia 引入模型生成代码、Shell、开放式 ReAct 工具、浏览器自动化或第三方进程内插件时，
评估独立 Sandbox Starter/服务。它需要容器/进程隔离、文件系统和网络策略、资源配额、超时销毁
与制品扫描，不与当前 Integration Sandbox Profile 混用。

## P3：文档国际化

不阻塞当前框架能力建设。出现稳定的英文使用者或对外交付需求后：

- 建立 `zh` / `en` 对等信息架构；
- 为 MkDocs 增加语言切换和独立搜索索引；
- 优先翻译 Quick Start、CLI、Python API 和错误目录；
- CI 检查中英文导航、代码示例和版本声明的一致性；
- API 契约、机器错误码和配置字段保持单一英文标识，不复制两套实现。

## 长期触发项：模型定制与生产体系

只有同时满足以下条件才启动评估：

- Prompt、Few-shot、Context 和 Workflow 仍无法解决稳定、重复的模型偏差；
- 有足够、合法、代表性的标注数据和独立验证集；
- 能定义基线、改善阈值、安全指标和回滚方案；
- 客户愿意承担长期数据治理、训练和模型运维成本。

届时可以独立评估 `model-factory/`，包括数据治理、标注、SFT/LoRA、评估、制品注册、发布和回滚。它不属于 Gaia 核心，也不应该为了展示技术能力而提前建设。
