# HR 参考应用

Gaia HR Showcase 用三个相互关联的员工服务场景，展示模型、企业知识、业务系统和人工确认如何
组合。它是独立参考应用，不会进入生成项目；你可以先体验结果，再选择最接近自己业务的模板。

三个场景都通过 Gaia 的五阶段安全装配运行。输入、检索结果、模型输出、工具参数和工具结果分别
留下无正文的决策证据；结构化模型输出由真实 Guardrails AI Validator 本地校验，模型调用、
预算、重试和审计仍由 Gaia 管理。

HR Showcase 位于仓库外的 `showcase/gaia-hr-suite`。`make demo` 会在依赖完整时尝试启动它，并
让 HR 工作台与 Dev Console 读取同一组 HR Run；缺少外部仓库、虚拟环境或前端依赖时，核心
Console 演示仍会继续，并明确报告 Showcase 不可用。建议以终端实际打印的 HR 地址为准，先在
业务端完成一次操作，再点顶部“查看本次 Run 证据”进入控制面。

- `make demo` 且 HR 启动成功：[打开 `4173` 上的 HR 参考应用](http://127.0.0.1:4173/)
- `make dev-full`：[打开 `4181/hr/` 上的 HR 参考应用](http://127.0.0.1:4181/hr/)

两种模式不能混用路径。完整端口和依赖见[选择运行与部署方式](runtime-profiles.md)。想单独运行，
见 HR Showcase 自己的 README。

演示路径：

1. 在 HR 工作台选择一个场景并发起请求。
2. 业务页面先展示人能理解的进度、草案与审批动作。
3. 点击“查看本次 Run 证据”，进入 Gaia Control Center 的同一条 Run。
4. 先阅读结果解释，再按需展开事件、审批、Guardrail 与 Tool 原始证据。

控制面会把业务信息和技术标识成对展示：主文案使用“HR 运营人员”“入职权限开通”“权限草案
超出岗位模板”等业务语言；相邻的次级信息保留 `hr-ops-li`、`hr.onboarding.access`、
`ACCESS_POLICY_VIOLATION` 等用户 ID、场景 ID 和错误代码，便于开发与审计定位，但不会再把
这些内部标识混进业务结论里。

## 三个场景分别证明什么

| 场景 | 模型什么时候介入 | 企业上下文 | 受控位置 |
| --- | --- | --- | --- |
| 入职权限开通 | 根据入职信息和岗位模板生成权限草案 | HR 入职记录、岗位权限模板 | 最小权限规则校验，IT 确认后逐项写入系统 |
| 员工政策与个人假期问答 | 把制度依据和个人数据整合成回答 | 员工手册、当前用户身份、HR 假期账户 | 检索权限和引用约束；只读，不执行写操作 |
| 请假办理 | 从自然语言中识别日期、假期类型、时长和原因 | 当前员工身份、假期余额、请假规则 | 余额与日期校验，经理批准后才提交 HR 系统 |

## 入职权限开通

用户提出：“请按产品经理岗位标准，为林夏准备入职账号和系统权限。”

执行链：

1. Read Tool 从 HR 系统读取入职记录，从权限系统读取岗位模板。
2. 模型根据两份信息生成账号和权限草案，但没有执行权限。
3. 确定性规则删除岗位模板以外的权限，并拆成即时通讯、邮箱、知识库和项目系统四个动作。
4. IT 管理员看到脱敏后的业务摘要并确认。
5. Gaia 按依赖顺序执行动作；某一步失败时保留已经成功的结果，并停止依赖它的后续动作。

这个示例重点不是“AI 自动开账号”，而是展示模型建议如何进入企业控制范围：模型负责处理
模糊信息，规则负责边界，人工承担授权，Runtime 负责幂等、恢复和审计。

## 员工政策与个人假期问答

用户提问：“我今年有几天年假？距离转正还有多久？”

执行链：

1. Retriever 根据当前身份检索员工手册中的年假和试用期条款。
2. Read Tool 从 HR 系统读取入职日期、转正日期、已用额度和当前余额。
3. 模型区分“制度规则”和“个人事实”，再生成个性化回答。
4. 页面分别展示制度引用和个人数据来源，避免把模型回答当成无来源结论。

这个示例说明 RAG 不必是一个孤立问答框。企业知识可以提供规则，业务系统提供实时事实，模型
负责把两者组织成用户能理解的答案。整个过程只有只读能力，不会因为提问触发系统写入。

## 请假办理

用户提出：“下周三请一天年假，参加家里活动。”

执行链：

1. 模型从自然语言中提取日期、假期类型、时长和原因。
2. Read Tool 查询当前员工的假期账户。
3. 确定性规则检查字段是否完整、日期是否有效、余额是否足够。
4. 页面生成待确认申请，直属经理批准前 `hris.submit-leave` 不会被调用。
5. 批准后 Gaia 执行写入，并记录工具调用和最终业务结果。

这个示例把普通表单与 AI 应用区分开：模型允许员工用自然语言表达不完整需求，企业规则确保
申请可执行，人工确认和受控 Tool 决定是否真正改变业务状态。

## 如何借用这些例子

- 总结、分类或抽取应作为完整业务链中的模型步骤，而不是单独建设一个孤立应用。
- 需要制度依据和实时个人数据时，参考员工政策问答的 Retriever + Read Tool 组合。
- 需要模型生成建议但不能直接执行时，参考入职权限开通的 Action Plan。
- 需要自然语言驱动单个业务动作时，参考请假办理的提取、校验、确认和写入链路。

在 Quick Start 中选择模板只会生成通用骨架和推荐组件，不会复制 HR 名称、数据或业务规则。
