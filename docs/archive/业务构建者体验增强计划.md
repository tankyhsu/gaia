# Gaia 业务构建者体验增强计划

状态：M6A 至 M6D 核心能力已实现，M6E 首轮验收完成
更新日期：2026-07-26

## 实施摘要

| 里程碑 | 当前状态 | 已实现边界 |
| --- | --- | --- |
| M6A | 完成 | 统一 ToolRegistry、Scoped Tool/Retriever、ScenarioContext tools/model/retriever、ToolInvocation、GaiaAppBuilder |
| M6B | 完成 | pending_result、独立 approval_view、等待态和终态持久化 |
| M6C | 完成首版 | 预生成 ActionPlan、严格顺序执行、逐动作审批、失败停止、重启恢复 |
| M6D | 完成首版 | ScenarioTestHarness、三类模板样本、轻量 TypeScript Client、CI 契约漂移检查 |
| M6E | 完成首轮并调整展示边界 | Quick Start、Dev Doc 和独立 HR Showcase 负责案例展示；日常 Console 只保留框架观测 |

当前明确不包含动态加步骤、并行执行组、计划级合并审批和自动补偿。这些能力必须由新的真实业务
需求触发，不作为首版 ActionPlan 的隐含承诺。

## 1. 目标

这一阶段不增加 Gaia 自己的 Agent Loop。目标是让应用构建者用普通 `Scenario` 就能更自然地
完成以下工作：

1. 调用企业知识、身份、业务系统等只读能力；
2. 调用模型并获得统一的观测与安全证据；
3. 把一个业务结果连同待确认动作交给前端；
4. 在一次业务请求中受控执行多个确定动作；
5. 用较少的装配代码启动、测试和观察完整应用。

未来接入 AgentScope、LangGraph 等成熟 ReAct 实现时，它们也必须复用同一套 Tool、Policy、
Human Gate、持久化和审计能力，不能另建一条绕过 Gaia Runtime 的执行通道。

## 2. 实施前的问题与处理结果

三个 HR Showcase 证明 Gaia 的受控写入主线可用，也暴露了普通应用构建过程中的摩擦。

| 问题 | 当前证据 | 对构建者的影响 |
| --- | --- | --- |
| 只读 Tool 没有统一执行入口 | 已由 `tools=`、统一 Registry 和 Scoped Tool Executor 解决 | 读取统一经过权限、超时、Guardrail 和证据链 |
| Scenario 上下文能力太少 | 已增加类型明确的 `tools` 与 `model` | 客户业务 Store 仍由应用 Adapter 持有，不引入 Service Locator |
| 应用装配偏底层 | 已增加 `GaiaAppBuilder` | 低层 `ApiDependencies` 保留给框架扩展和兼容代码 |
| 等待人工时业务结果丢失 | 已增加 `pending_result` 与 `approval_view` | 前端不再读取执行 Payload |
| 一次 Run 只能提出一个副作用 | 已增加版本化 `ActionPlan` | 首版只支持严格顺序的预生成计划 |
| 前端接入重复处理 Runtime 细节 | 已增加 TypeScript `GaiaClient` | HR Showcase 已迁移创建 Run、读取 Gate、审批和统一错误映射 |
| 参考应用没有完整消费 Gaia 能力 | HR Showcase 已消费 Scoped Retriever、Read Tool、Model、Guardrail、Gate 与 ActionPlan | 参考 Retriever 是可替换应用 Adapter，生产可换成 `rag-postgres` |

这些问题不是通过加入 ReAct 就能解决的。相反，如果现在直接接 Agent，装配、工具执行和运行
状态的不一致会被循环放大。

## 3. 设计原则

### 3.1 Scenario 仍是业务入口

简单应用继续使用普通异步函数。构建者不需要为了调用两个工具或执行三步确定流程而引入 Agent。

### 3.2 读取可以执行，写入只能提案

- Read Tool 经过 Scope、角色、环境、超时、Guardrail 和观测后可以在 Scenario 中直接调用；
- Write Tool 不能被 Scenario 或第三方 Agent 直接执行，只能形成受 Runtime 管理的动作提案；
- Mock、Sandbox、Customer 环境仍由服务端配置决定。

### 3.3 Gaia 提供能力端口，不提供业务服务定位器

`ScenarioContext` 可以获得类型明确的 Model、Tool 和 Retrieval 能力，但不增加任意
`dict[str, object]` 形式的 Service Locator。客户数据库、规则和系统连接继续通过应用 Adapter
实现。

### 3.4 业务状态与技术状态分离

“已经生成的方案”“等待谁确认”“哪些动作尚未执行”“最终执行结果”必须是不同字段。前端不应
从副作用 Payload 或 Event 日志反推业务页面。

### 3.5 Showcase 只做验收

能力先进入 Gaia 公共契约和测试，再由独立 Showcase 消费。Gaia Core 不引用 HR 名称、数据或
流程。

## 4. 目标构建体验

下面的 API 形状用于说明目标，不是已经冻结的公共契约：

```python
@read_tool("hr.get-employee-profile", required_roles=("employee",))
async def get_employee_profile(employee_id: str) -> EmployeeProfile:
    ...


@write_tool(
    "iam.grant-access",
    risk_level=RiskLevel.MEDIUM,
    required_roles=("it-admin",),
    reconcile=reconcile_access,
)
async def grant_access(...):
    ...


@scenario(
    "hr.onboarding.access",
    allowed_tools=("hr.get-employee-profile", "iam.grant-access"),
)
async def provision_access(context: ScenarioContext) -> ScenarioResponse:
    employee = await context.tools.call(
        get_employee_profile,
        employee_id=context.metadata["employee_id"],
    )
    plan = await context.model.generate_structured(...)
    action = context.tools.propose(
        grant_access,
        step_id="grant-access",
        payload={"employee_id": employee.data["id"]},
        reason="Access changes require approval.",
    )
    return ScenarioResponse.propose_plan(
        pending_result={"access_plan": plan},
        actions=(action,),
    )


app = (
    GaiaAppBuilder(config)
    .model(model_provider)
    .scenarios(provision_access)
    .tools(get_employee_profile, grant_access)
    .build()
)
```

构建者只声明业务场景、可用能力和 Adapter。Model 的观测、Guardrail，Read Tool 的授权与证据，
以及 Write Tool 的 Gate、幂等和恢复由 Gaia 统一处理。

## 5. 分阶段实施

## M6A：统一能力装配与只读 Tool 执行（P0）

### 交付物

- 引入统一 `ToolRegistry`，同时登记 Read Tool 和 Write Tool；
- 引入受 Scope 约束的 `ToolExecutor`；
- 为 `ScenarioContext` 提供类型明确的 `tools` 和 `model` 能力；
- `ApiDependencies.from_scenarios()` 接受统一 `tools=`，旧 `write_tools=` 保留一个兼容周期；
- Read Tool 自动执行角色、环境、白名单、超时和 Guardrail 检查；
- 新增 `ToolInvocation` 证据，至少记录 Run、Tool、版本、耗时、状态、错误码及输入输出哈希；
- Write Tool 通过 `context.tools` 调用时只返回动作提案，不允许直接触达 Adapter；
- 提供 `GaiaAppBuilder` 或等价的高层装配入口，把 Provider 包装、Registry 和 Runtime 创建收敛
  到一处。

### 验收

1. 一个 Scenario 可依次调用身份 Read Tool、RAG Retriever 和模型，不需要闭包注入；
2. 未列入 `allowed_tools`、角色不符或环境不符的读取在调用前被阻断；
3. Read Tool 成功、超时、异常和 Guardrail 阻断都有统一证据；
4. 生成项目能用不超过一处 Composition Root 注册 Scenario、Model 和 Tool；
5. 现有单副作用应用不修改业务行为即可迁移。

## M6B：等待态业务输出与审批展示契约（P0）

### 交付物

- 为 Run 增加 `pending_result`，允许 Scenario 在提出动作时保存已生成的业务结果；
- 为动作提案增加独立 `approval_view`，存放经过脱敏的标题、摘要、字段和风险说明；
- `HumanGate.requested_action` 继续作为执行载荷快照，但不再承担前端展示协议；
- Run Snapshot 同时返回 `pending_result`、待确认摘要和 `pending_gate_id`；
- 审批通过后保留 `pending_result`，并将执行结果写入终态 `result`；
- 拒绝、过期和取消时保留可审计的业务草稿与决策原因。

### 验收

1. 前端只查询 Run Snapshot 就能展示“模型生成了什么、正在等什么、尚未执行什么”；
2. Gate Payload 增删内部字段不会破坏业务页面；
3. `waiting_human` 时 Write Adapter 调用数仍为零；
4. API、SSE、诊断包和 Dev Console 对等待态使用同一语义。

## M6C：确定性多动作执行计划（P1）

### 交付物

- 将单个 `side_effect` 扩展为版本化 `ActionPlan`；
- 每个 `PlannedAction` 有独立 Tool、风险、依赖、审批、幂等键和状态；
- 首版只支持预先生成的有向无环计划和严格顺序执行，不支持运行中自行增加步骤；
- Runtime 持久化计划、游标和每个动作的执行证据；
- 支持按动作审批；计划级合并确认留待真实审批域需求验证；
- 失败默认停止后续动作并报告 `partial`，不承诺自动补偿；
- 已执行动作继续使用 `reconcile` 处理超时未知状态；
- Run Snapshot 返回计划总览及每个动作的 `pending / waiting_human / executing / succeeded /
  failed / skipped` 状态。

### 验收

使用“新员工账号与权限开通”证明：

1. HR 身份读取是 Read Tool；
2. 模型只生成建议计划，确定性 Policy 决定允许的权限范围；
3. IAM、邮箱和项目系统是三个独立 Write Tool；
4. 审批前所有写入为零；
5. 第二个动作失败时，第一个动作保持成功、第三个动作不执行，Run 明确报告部分完成；
6. 重启后从未完成动作继续，不重复执行已成功动作。

## M6D：构建者测试与客户端 SDK（P1）

### 交付物

- `ScenarioTestHarness`：注入 Mock Model、Read Tool、Retriever 和 Write Proposal Recorder；
- 断言 Read Tool 调用、模型调用、动作计划、Gate 和最终结果，不要求测试直接访问 Runtime 内部表；
- `gaia init` 为三类模板生成一条正常样本、一条权限/规则边界样本和一条依赖失败样本；
- 从 OpenAPI 生成或校验轻量 TypeScript `GaiaClient`；
- 客户端提供 `createRun`、`watchRun`、`decideGate`、`cancelRun` 和统一错误类型；
- `watchRun` 内聚 Snapshot、SSE 重连和终态判断，业务前端不再自行拼状态机。

### 验收

1. 构建者可以在不启动 HTTP 服务的情况下验证 Scenario 主线；
2. 相同 Dataset 可在 Mock 和 Sandbox Profile 下运行；
3. Showcase 删除自行实现的 Run 轮询、Gate 解析和错误映射后功能不回退；
4. Python 公共契约、OpenAPI 与 TypeScript Client 在 CI 中检查漂移。

## M6E：构建者引导与真实组合验收（P2）

### 交付物

- Quick Start 提供三个独立 Showcase 入口，帮助构建者先理解可实现的业务体验；
- Dev Doc 按模型介入、企业上下文、规则和受控写入拆解三个案例；
- 日常 Dev Console 不展示 Showcase 内容，只保留组件、运行、配置、Prompt 和测试；
- 技术事件、哈希和内部错误仍由 Run 诊断页面展示；
- HR Showcase 的知识场景改为真实消费 Gaia RAG、Read Tool、Model 和 Guardrail；
- HR Showcase 的入职场景改为消费 `ActionPlan`，不使用聚合“大工具”模拟多系统写入。

### 验收

业务构建者能回答以下问题，而不需要阅读 Trace JSON：

- 这次请求读取了哪些资料和系统？
- 模型产生了什么建议，确定性规则改了什么？
- 哪些动作需要谁确认？
- 哪些动作已经执行，哪些没有执行，失败后能否重试？
- 当前结果使用了哪个 Prompt、模型、知识版本和规则版本？

## 6. 与成熟 ReAct Agent 的未来边界

M6 不实现 Agent Loop，但 M6A 至 M6D 必须让未来 Agent Adapter 有稳定的接入面。

### 6.1 Gaia 负责什么

- Model Gateway 与调用观测；
- Tool Schema、注册、授权、环境绑定和执行；
- Retrieval 与 Context 端口；
- Guardrail；
- Run、预算、Checkpoint、Human Gate、Action Plan、幂等、恢复和审计。

### 6.2 第三方 Agent 框架负责什么

- ReAct / Plan-Execute 循环；
- 下一步 Tool 选择；
- Agent 内部状态和上下文压缩；
- 框架自身的 Planner、Memory 和多 Agent 协作策略。

### 6.3 预留协议

后续单独评审 `AgentRuntimeAdapter`，用于接入 AgentScope、LangGraph 等成熟实现。Adapter 获得的
不是原始 Provider 和任意 Python 函数，而是 Gaia 下发的受限执行上下文：

```python
@dataclass(frozen=True)
class AgentExecutionScope:
    scenario_id: str
    allowed_tools: tuple[str, ...]
    model_profile: str
    context_profile: str
    guardrail_profile: str
    max_steps: int
    max_model_calls: int
    max_duration_seconds: int
    write_mode: WriteMode
```

关键约束：

- Read Tool 可以通过 Scoped Tool Executor 返回 Observation；
- Write Tool 只能返回 Action Proposal Receipt，实际执行仍由 Gaia Runtime 决定；
- Agent 暂停等待审批时，第三方框架必须提供可持久恢复的 Checkpoint；
- 第三方 Agent 的 Trace 可作为补充证据，但不能替代 Gaia 的 Tool、Gate 和 Side Effect Ledger；
- Agent Adapter 不能改变生产 Profile、扩大 Tool 白名单或关闭强制 Guardrail；
- 代码执行、Shell、浏览器自动化仍需独立 Sandbox 评审。

因此，M6 不是“先做一半 Agent”，而是在把 Agent 将来必须依赖的企业执行底座先做完整。

## 7. 推荐顺序

| 顺序 | 里程碑 | 原因 |
| --- | --- | --- |
| 1 | M6A 统一装配与 Read Tool | 后续多动作、测试和 Agent Adapter 都依赖统一能力入口 |
| 2 | M6B 等待态业务输出 | 修复当前 Showcase 已经出现的错误前端耦合 |
| 3 | M6C Action Plan | 提升受控执行的真实业务上限，同时不引入开放循环 |
| 4 | M6D Test Harness 与 Client | 降低每个新应用重复建设和回归成本 |
| 5 | M6E 工作台与 Showcase 验收 | 在公共契约稳定后做可视化，避免 UI 反向定义 Runtime |

完成 M6C 后再进行一次真实应用评审，决定是否开始 Agent Adapter Spike。不要把“能够实现一个
循环”当成开工条件；开工条件应是某个真实场景已经无法用确定性 Workflow 或 Action Plan 清晰
表达。

## 8. 明确不做

- 不在当前阶段实现 Gaia 自有 ReAct Loop；
- 不把所有 Scenario 自动编译为 Agent；
- 不允许模型在运行中动态扩大 Tool 集合；
- 不允许 Read Tool 绕过权限、环境、Guardrail 和观测；
- 不让 Write Tool 因第三方 Agent 接入而绕过 Human Gate；
- 不为多动作计划承诺通用分布式事务或自动补偿；
- 不把 Dev Console 变成生产业务后台；
- 不因 Showcase 需求向 Gaia Core 写入 HR 业务字段。
